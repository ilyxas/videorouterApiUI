## Цель и границы

Сделать ежедневную работу предсказуемой: пользователь выбирает задачу, видит необходимые входы, связывает результаты, понимает цену и может вернуться к работе после перезагрузки или ошибки.

**Явно запрошено пользователем:** значительное улучшение workflow, автоматизации и UX/UI input/output. Это основное направление плана, не косметическая задача в конце списка. Подробности: [03-workflow-input-output.md](03-workflow-input-output.md).

Визуальные референсы задают принцип «тип медиа → действие → подходящие входы/модель/настройки», а не обязательную тёмную тему, точные модели или тарифы.

Этапы 1–3 образуют первую полезную поставку. Они готовят основу значительного улучшения workflow, а не откладывают его до полной переработки всех разделов. После обязательного replan этап 4 внедрять проверяемыми группами операций, не создавать видимость поддержки всего API сразу.

## Сквозные критерии

- Черновики и конфигурации не теряются при переключении экранов, режима/модели и reload.
- Пользователь видит что входит в шаг, откуда это берётся и какой результат получится.
- Для связи не нужны знания пути JSON в ответе провайдера.
- Размер, формат, длительность, количество результатов и обязательные входы проверяются с учётом конкретной модели/провайдера.
- Не допускается молчаливый выбор первого результата из нескольких или автоматический выбор «лучшего» без объявленного правила.
- Поддерживается цепочка нескольких зависимых шагов после одного осознанного запуска; не требуется вручную переносить каждый результат.
- Ожидаемая стоимость, верхняя оценка и фактически учтённые расходы различаются. Неизвестная часть стоимости видна.
- Технические upload/polling операции не перегружают основной редактор, но доступны в деталях и правильно учитываются в статусах/расходах.
- API Explorer остаётся доступен для расширенных запросов; удобный workflow не сводится к набору форм с именами HTTP-полей.

## Проверка без платных действий

Для реализации нужны локальные фикстуры ответов и подменяемый транспорт. Проверять переходы request → result → binding → следующий request, ошибки совместимости, несколько результатов, просроченный URL, сохранение/восстановление и статусы асинхронного задания. Не выполнять платную генерацию как часть автоматических тестов.

Один сфокусированный проход UI должен охватывать основной сценарий, исправление ошибки, повторное открытие и ширину телефона. Не расширять его в бесконечный редизайн или повторять успешные проверки без изменения затронутого кода.

Для необходимых API-проверок пользователь предоставил $10 без повторного approval; в этих итерациях израсходовано $0, выполнены только бесплатные оценки. Этот бюджет не означает требование тратить его при подготовке документации/replan и не заменяет технический контроль расходов. Платный end-to-end пока не выполнялся.

## Что не включено автоматически

- Победители, рейтинги друзей/ИИ и сравнение качества моделей.
- Графический бесконечный canvas как обязательный вид редактора: последовательные карточки с явными связями могут решить основную задачу.
- Общий визуальный язык программирования с циклами, параллельными ветками и произвольными выражениями.
- If/Else и произвольные решения между шагами из старой переписки. Необходимый выбор конкретного output при `n > 1` относится к текущей задаче; универсальные решения — отдельный объём.
- Webhook-сервер, публичный хостинг, аккаунты нескольких пользователей, новые интеграции.
- Жёсткий лимит реального биллинга без подтверждённых возможностей API. Бюджетная оценка сама по себе не гарантирует такой лимит.

## Риски реализации

Изменение хранения связей требует совместимости со старыми positional refs; миграцию выполнять с резервной копией и проверкой чтения старых workflow. Нельзя подменять реальные контракты догадками по скриншотам или тарифам. Замена модели способна менять не только цену, но и тип входа/выхода, ограничения и маршрутизацию. TTL ссылок и остановка сервера требуют явных состояний, а не скрытого повторного платного запуска.
