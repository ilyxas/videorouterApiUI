## Следующее действие: replan архитектуры workflow

Пользователь прямо потребовал: **до продолжения step 4 сначала перепланировать архитектуру workflow**. Этот replan ещё не выполнен. Текущая задача — передать достоверное состояние, а не реализовать новую архитектуру.

Предлагаемые вопросы для replan (это рабочая повестка, а не уже принятое архитектурное решение):

1. Разделить пользовательский workflow, контракт действия, параметры модели/провайдера и технический план исполнения. Сейчас значительная часть логики находится в `public/app.js`.
2. Определить единое представление портов, артефактов и зависимостей, учитывая уже сохранённые стабильные ID и старые `{{N.path}}` ссылки. Сейчас типизированный адаптер полноценнее всего реализован для изображений.
3. Явно разделить предварительную оценку неполного шага, строгую проверку запуска и оценку фактического разрешённого запроса перед генерацией. Не требовать готовности медиа для ориентировочной цены.
4. Развести факты каталога, проверенные ограничения профилей и неизвестные возможности. Широкий выбор моделей не означает проверку всех сочетаний; узкий whitelist не должен заменять каталог.
5. Определить расширение input/output адаптеров, обработку ошибок и состояния async jobs без скрытого повторного платного создания.
6. Подготовить план совместимой миграции и проверок, затем пересобрать оставшийся этап 4 в небольшие поставки. Не перезаписывать существующие workflow/историю/assets и не добавлять DAG/параллельность/If-Else только ради новой архитектуры.

Результат replan: документ с выбранными границами модулей, моделью данных, миграционным подходом, критериями приёмки и обновлённой последовательностью этапа 4. Технические решения и реализация этого плана относятся к следующей задаче.

## Что работает сейчас

| Область | Реализовано | Предел утверждения |
|---|---|---|
| Черновик | localStorage, сохранение незавершённого JSON, стабильные ID, reload | Один черновик на origin; данные браузеров/адресов не синхронизируются |
| История | Снимок исходного workflow и технического плана, фактические запросы, открытие как нового черновика | Старые записи без конфигурации не восстановлены задним числом |
| Image | Создать / редактировать / увеличить; формат/качество и модель; явный выбор output | Edit/upscale в удобном сценарии используют один reference; не все каталожные режимы проверены |
| Связи | Image → edit → upscale → video по ID/порту/индексу; URL/base64; ожидание и блокировка зависимых шагов | Нет выбора пользователем после генерации, межзапускового reuse и универсальных типизированных адаптеров всех медиа |
| Модели | Image/Video берутся из статического и загруженного каталога, учитываются capabilities и известные профили | Остальным моделям предлагаются общие параметры endpoint; сочетания размеров могут быть изменены API |
| Оценка | Отдельный неполный шаг можно оценить без prompt/будущего output; пропуски и допущения видны | При cannot_estimate или токенной цене числовое значение не выдумывается |
| Генерация | Полная проверка и разрешение входов, уточнение цены, сравнение явных assumptions с запросом | Проверяются только возвращённые assumptions; это не проверка размеров готового файла и не лимит расходов |
| Редактор | Вставка после шага, перенос с защитой зависимостей, сворачивание, навигация, возврат из API-редактора | Полный аудит доступности/клавиатуры и повседневных мобильных сценариев не выполнен |
| Видео/аудио | Text/image/audio-to-video, отдельный lip-sync; TTS/transcription/upload | Reference/edit/extend/motion-control/upscale video явно недоступны. Расширение аудиосценариев не завершено |

Список «8 Video» в коде включает audio-to-video, а референсы пользователя включают lip-sync. Lip-sync остаётся отдельным действием/endpoint; не смешивать эти перечни.

## Изменения, которые нельзя потерять при replan

- Автосохранение, sourceStepId, исходные/фактические параметры запуска и восстановление черновика из истории без отправки API.
- Явно выбранный номер изображения при n > 1; отсутствие автоматического fan-out и повторной платной генерации при ошибке/истёкшей ссылке.
- Длительность видео 5 секунд не заменяется на 8 секунд только в оценке из-за длины аудио.
- `previewEstimate()` работает по одному шагу; не вызывает `compileWorkflow()` для всей цепочки, не загружает файлы и не выполняет зависимости. Неразрешённые ссылки исключаются из предварительного запроса с уведомлением.
- Перед генерацией оценка использует готовые фактические параметры. Расхождение в явно возвращённых assumptions останавливает генерацию; при предварительной оценке оно показывается пользователю без блокировки.
- GPT Image 1 получает явные defaults `size=1024x1024`, `quality=medium`, одинаковые в форме/оценке/генерации. Причиной пустой цены было `standard`, которого нет в тарифах этой модели.
- Каталог не ограничивается одной Image-моделью и LTX. Пустой audio picker не ограничивает список видео; заполненный одиночный аудиовход ограничивает его поддерживаемыми LTX-профилями.
- Несовместимые сохранённые значения не удаляются молча при смене модели.

- Браузерный проход цепочки из пяти шагов и ширины 390 px — фикстуры. Последующий проход исправления цены/моделей/формата — настоящий API оценки через тестовый relay, допускавший только pricing/estimate.
- 6 бесплатных реальных оценок: 3 диагностика и 3 браузер. Платные генерации и внешние загрузки в этих проверках не выполнялись; подтверждённый расход этих итераций — **$0**.
- Пользователь неоднократно предоставил **$10 на необходимые API-проверки без дополнительного approval**. Бюджет этих работ не использован; он не покрывает произвольные сторонние платные действия. Новые действия должны соответствовать актуальному поручению пользователя и применимым правилам среды.
- Реальный платный end-to-end и качество полученного медиа не проверены. Проверка доступности Tailscale выполнена с Mac, не с телефона.

Тестовый relay и временные БД не включены в приложение. Исторический исходный SHA-256-манифест и скриншоты аудита не представляют текущую версию.

## Запуск: важная поправка после последнего исправления

Два прежних сообщения «сервер и Tailscale перезапущены» оказались неверными: `studio.sh restart` сообщал об успехе во время команды, но позднее оба процесса отсутствовали. Лог не показал точной причины завершения. **Не утверждать, что причина выхода окончательно диагностирована.**

После замечания пользователя оба процесса запущены напрямую через разовые пользовательские задания `launchd` (`launchctl submit`). Отдельная последующая команда подтвердила PID, HTTP обоих адресов и наличие обновлённого contracts-модуля. Это не постоянный LaunchAgent и не настройка автозапуска после login/reboot.

Последний подтверждённый снимок, а не обещание текущей доступности:

| Процесс | PID на проверке | Разовое задание |
|---|---|---|
| server.mjs | 16404 | `local.videorouterapiui.server.1794941547` |
| tailscale.mjs | 16411 | `local.videorouterapiui.tailscale.1794941547` |

- Mac: `http://127.0.0.1:8791`.
- Tailscale с Mac: `http://100.80.72.44:8791`; разрешённый телефон `100.121.194.63`.
- `data/launcher.pid` и `data/tailscale.pid` записаны для совместимости со `studio.sh status/stop`.
- После этого запуска `api_connected=false`: ключ из прежней памяти сервера не сохранился. Ключи в Handoff не переносились.
- **Сам `studio.sh` не переведён на launchd**: start/restart всё ещё создают фоновые процессы через nohup. Не считать эту проблему устранённой в коде launcher. Временный helper использовался из `/Users/ilya/Documents/Codex/2026-11-17/ghj/work/durable-launch/start.py`, он не является частью проекта или универсальным launcher и содержит тогдашние адреса/порт.

В новом thread не перезапускать сервис без необходимости. Если понадобится запуск/перезапуск, учитывать активные задания, обязательную пару server + proxy, текущие адреса и новые PID. **После завершения команды запуска отдельной командой проверить оба процесса и HTTP**, а не повторять только строку успеха скрипта. Повторное использование launchd-label требует сначала проверить, существует ли такое задание; не останавливать чужие процессы и не настраивать автозапуск без соответствующего поручения.
