# Workflow: операции, входы, выходы и автоматизация

Обновлено: 2026-11-17. **Требования и предложения для workflow; реализован только их поднабор.** Актуальный статус — [09](09-current-state-and-next-thread.md). По последнему указанию пользователя до продолжения этапа 4 сначала требуется replan архитектуры workflow. Предложения ниже — материал для replan, не уже выбранная новая архитектура.

## Требование пользователя

Каждый шаг представляет понятное действие над медиа, опирающееся на запрос API. Пользователь выбирает действие из конечного понятного списка, получает соответствующую форму и может напрямую связать output с совместимым input следующего шага. Обязательный пример: генерация изображения → использование этого изображения в следующем запросе, например создание видео.

Автоматизация означает выполнение заданных зависимостей после запуска workflow: дождаться результата, извлечь выбранный артефакт, при необходимости выполнить разрешённую подготовку, собрать следующий запрос и продолжить. Пользователь не должен копировать URL и разбирать JSON между шагами.

Это не требование копировать внешний стиль. Пользовательские скриншоты сохранены в [references](references) и описаны в [реестре доказательств](04-evidence-and-references.md).

## Что показывают референсы

**Image: 3 действия** — Text to Image, Edit Image, Upscale Image.

**Video: 8 действий** — Text to Video, Image to Video, Reference to Video, Edit Video, Extend Video, Motion Control, Upscale Video, Lip Sync.

Видимые принципы:

- Сначала семейство Image / Video / Audio, затем задача.
- Форма изменяется по выбранной задаче; для редактирования/референсов появляется место добавления медиа.
- Модель, соотношение сторон, количество, длительность, разрешение и цена собраны рядом с действием генерации.
- Различаются ожидаемая цена и максимум при fallback.

Референсы не показывают само связывание шагов: это отдельное явное требование пользователя. Наличие вкладки Audio не даёт списка её режимов. Цены и выбранные модели на скриншотах не считать актуальными данными.

## Важное различие: действие, endpoint, модель

Не создавать отдельный endpoint для каждой кнопки. Несколько действий могут использовать один endpoint с разными полями и ограничениями моделей. Lip Sync использует отдельный `/v1/lipsync`. Один пользовательский шаг может требовать технических запросов upload/status; они остаются видимыми в деталях, а не превращаются в обязательную ручную работу.

В текущем локальном коде `videoModes` тоже содержит восемь обозначений, но **другие восемь**: включает audio-to-video и не включает lip-sync. Нельзя механически принять этот объект за список со скриншота. Сохранить доступный аудио→видео сценарий и проверять полный набор по актуальному API; не ограничивать продукт навсегда числами 3 и 8. Публичный локальный каталог изображений также содержит virtual-try-on.

## Матрица действий для реализации

Это проектируемый UX-контракт. Endpoint-кандидаты взяты из локального каталога; точные поля, формы ответов и возможности конкретных моделей необходимо сверить с официальной документацией перед реализацией.

| Действие | Вход по смыслу | Выход | Привязка к API / что проверить |
|---|---|---|---|
| Text to Image | Текст и настройки | Одно или несколько изображений | `POST /v1/images`; доступность параметров по модели. |
| Edit Image | Изображение(я), инструкция | Изображение(я) | `/v1/images`, структура `input_references` и дополнительные поля зависят от контракта. |
| Upscale Image | Изображение, масштаб/целевой размер | Изображение | `/v1/images` как кандидат по каталогу; проверить модель и `scale_factor`. |
| Text to Video | Текст | Видео | `POST /v1/videos`; длительность, размер, ограничения модели. |
| Image to Video | Изображение и инструкция | Видео | `/v1/videos`, `start_image_url` для поддерживаемых моделей; конечный кадр — отдельный порт, если разрешён. |
| Reference to Video | Набор поддерживаемых референсов и текст | Видео | `/v1/videos`; различать `input_references`, `input_video_references`, `input_audio_references`, структуру каждого элемента и лимиты. |
| Edit Video | Видео и инструкция | Видео | `/v1/videos`; проверить `input_video_url` и model-specific поля. |
| Extend Video | Видео или идентификатор исходного задания, параметры продолжения | Видео | Нельзя предполагать, что любой URL подходит: проверить отдельный контракт режима/модели. |
| Motion Control | Управляющее движение и визуальный источник | Видео | `/v1/videos` как кандидат; проверить роли входов, типы и обязательные комбинации. |
| Upscale Video | Видео, масштаб/размер | Видео | `/v1/videos`; проверить модель и режим масштабирования. |
| Lip Sync | Аудио + портрет **или** видео | Видео | `POST /v1/lipsync`: `audio_url` + поддерживаемый `image_url` или `video_url`; не считать все три входа взаимозаменяемыми. |
| Audio to Video | Аудио, при необходимости изображение/текст | Видео | Существующий сценарий `/v1/videos` с `input_audio_url`; отдельно от lip-sync, ограничения модели/провайдера. |
| Озвучить текст | Текст, модель, голос | Аудио | `/v1/audio/speech`; учитывать обязательность голоса и бинарный ответ. |
| Расшифровать аудио | Аудио | Текст/структурированный результат | `/v1/audio/transcriptions`; multipart/file и формат результата. |

Другие операции остаются в API Explorer до появления проверенного удобного контракта. Для каждого режима хранить: endpoint/method, обязательные/необязательные входы, ограничения типов/количества/размеров/длительности, допустимые модели, параметры оценки, адаптер ответа, источник и дату проверки схемы.

## Предлагаемый UX шага

1. **Добавить действие:** выбрать семейство и режим, затем найти совместимую модель. При добавлении из результата предыдущего шага сразу отфильтровать подходящие действия.
2. **Входы:** подписанные слоты («Стартовое изображение», «Запись речи», «Видео для движения»), в каждом источники «Файл», «URL», «Из шага» только если применимо.
3. **Параметры:** основные настройки рядом, расширенные раскрываются отдельно. Размер исходника, запрошенный размер и ожидаемый формат результата различаются явно.
4. **Выход:** до запуска — тип и ожидаемое число результатов; после — миниатюра/плеер, метаданные, выбор конкретного результата и действие «Использовать в следующем шаге».
5. **Связь:** у принимающего слота показывать «Шаг … → Изображение …», роль входа и возможность изменить/убрать связь. Не показывать сырой JSON-path как основной интерфейс.
6. **Сводка:** в свёрнутой карточке остаются действие, модель, входы/выход, размер, цена, статус. Выбранная карточка раскрывается без потери контекста всей цепочки.

Оба направления равноправны: от output нажать «Использовать…» или из input выбрать «Из шага». Создать связь можно **до** генерации; UI показывает ожидаемый результат, затем заменяет placeholder фактическим артефактом.

## Типизированные артефакты и связи — предложение реализации

Рекомендуется отделить внешние ответы API от внутреннего результата шага:

- Артефакт: стабильный ID, тип image/video/audio/text/structured, MIME при наличии, locator (локальный asset ID, HTTPS URL или иной подтверждённый контрактом источник), размеры/длительность при наличии, происхождение run/step/output, срок доступности если известен.
- Порт входа: семантическая роль, допустимые типы, один/несколько элементов, обязательность и ограничения модели.
- Связь: стабильный ID шага-источника, имя выхода, выбор элемента/объявленное правило, ID входного порта назначения. Порядковый номер карточки — только отображение.
- Адаптер результата: извлекает артефакты из конкретного ответа endpoint/провайдера; не предполагает общий `data.0.url` для всех операций.
- Адаптер запроса: преобразует связанные артефакты в правильное поле и структуру API, отличая URL от multipart file, одиночный вход от массива референсов.

Пример связи, не готовая схема хранения/API:

```json
{
  "from": {"stepId": "create-image", "port": "images", "selection": {"index": 0}},
  "to": {"stepId": "animate-image", "port": "startImage"}
}
```

`index: 0` допустим только как явно выбранное правило, а не скрытое поведение при нескольких результатах. JSON приведён для разработчика, пользователь создаёт связь через UI.

## Валидация и автоматическое исполнение

- Проверять совместимость по назначению входа, MIME/типу, количеству, выбранной модели/провайдеру, размеру и длительности. Не ограничиваться проверкой «это URL».
- Переключение модели/режима повторно валидирует связи; несовместимые значения не удаляются молча. Показать что требует исправления, инвалидировать оценку.
- До запуска обнаруживать отсутствующие входы, циклы и ссылки на удалённые/недоступные шаги. В первой последовательной версии разрешать зависимости только от предшествующих шагов; графический DAG и параллельность не обязательны.
- Исполнять зависимый запрос только после готовности требуемого результата. Если для источника отключено ожидание, явно объяснить и согласовать необходимое ожидание, а не передавать job ID вместо медиа.
- Локальный файл при необходимости загружается в API; уже подходящий удалённый URL не загружается повторно без причины. Не отправлять localhost URL провайдеру. Подготовка/конверсия должна соответствовать формату и быть показана в плане, с учётом расходов; не добавлять скрытую платную трансформацию.
- Если ответ содержит несколько результатов, пользователь заранее выбирает объявленное правило либо workflow останавливается в состоянии «Нужен выбор результата». Это узкая пауза выбора output, не универсальный движок решений.
- При сбое источника зависимые шаги помечаются заблокированными, не остаются неопределённо «Ожидание». Указать причину и действие исправления.
- При истечении URL/отсутствии файла показать проблему до следующего запроса, если её возможно определить локально; не запускать источник заново автоматически с новой оплатой.
- Сохранять отображение пользовательских шагов в технические запросы, чтобы прогресс и стоимость относились к понятному действию.
- Кнопка запуска на отдельном шаге/повторный запуск должны явно показывать, какие зависимости будут использованы и какие запросы отправлены; не перезапускать всю цепочку скрытно.

## Цена и зависимости

Предварительную оценку рассчитывать по заполненным параметрам выбранного шага, не блокируя её из-за незаполненного prompt или будущих медиа. Показывать пропущенные входы и допущения. Перед генерацией отдельно оценивать нормализованный запрос с фактическими входами, который действительно будет отправлен. Если цена зависит от ещё неизвестной длины/размера результата предыдущего шага, показывать допущение или диапазон, а не точное обещание. После появления фактических метаданных пересчитать зависимую оценку перед отправкой и сообщить об изменении согласно заранее выбранной политике пользователя.

Бюджетный подбор моделей должен учитывать совместимость всей цепочки: формат выхода, нужные входы следующего шага, размер, длительность и режим. Дешёвая модель, разрывающая связь, не считается подходящей заменой. Политика остановки при превышении оценки и реальный биллинговый лимит — разные вещи; не обещать второе без поддержки API.

## Сценарии приёмки

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| W01 | Текст → одно изображение → видео | Связь создаётся до запуска в UI. После получения изображения video request содержит правильный стартовый вход; копирование URL/JSON не требуется. |
| W02 | Изображение → редактирование → масштабирование → видео | Каждый выход предлагается совместимым input; все три перехода сохраняются после reload. Размер результата не подменяется размером исходника. |
| W03 | TTS + изображение → lip-sync | Два входа связаны с разными источниками; используется `/v1/lipsync` и правильные поля; бинарное аудио подготовлено корректно. |
| W04 | Генерация `n > 1` | Показаны все артефакты. Следующий шаг использует явно выбранный элемент/правило; при ручном выборе ожидает его. Нет скрытого fan-out платных запросов. |
| W05 | Несколько референсов → видео | Порядок, роли и количество сохраняются; используются нужные API-массивы и элементы, а не произвольный список строк. |
| W06 | Подключение audio к image-only порту | UI объясняет несовместимость, запуск заблокирован до исправления, исходная связь/выбор не теряются молча. |
| W07 | Перемещение/удаление шага | Перемещение сохраняет источник по ID либо объясняет недопустимый порядок. Удаление сообщает о зависимостях; нет случайного подключения к другому шагу. |
| W08 | Смена модели или режима | Совместимые значения сохраняются; неподдерживаемые входы/размеры требуют явного исправления; оценка устаревает. |
| W09 | Асинхронное задание → следующий шаг | Следующий запрос не отправляется до готовности медиа. Ошибка источника блокирует зависимый шаг с причиной. |
| W10 | Reload/остановка и повторное открытие | Черновик и связи восстановлены. История содержит снимок параметров; проверка существующего job не создаёт новую генерацию. |
| W11 | Истёкший URL или отсутствующий asset | Понятная ошибка входа; нет автоматической повторной платной генерации источника. |
| W12 | Оценка зависит от результата предыдущего шага | Неизвестные метаданные обозначены; после получения данных оценка уточняется, конфигурация оценки соответствует отправке. |
| W13 | Пять шагов на desktop/390 px | Видны последовательность и связи; можно редактировать любой шаг, выбрать output и запустить без ручной работы с API. |

W01 и цепочка W02 уже реализованы и проверены на фикстурах; W02 не подтверждает фактические размеры/качество у реального провайдера. Для W04 реализован заранее выбранный output, но не ручная пауза после получения результатов. Остальные сценарии выполнены лишь частично либо не выполнены; это критерии, а не список пройденных проверок. В новом thread сначала replan, затем выбор следующей группы этапа 4.

## Что требуется уточнить по API в реализации

Для каждого режима сверить официальные документы: [images](https://videorouter.sh/docs/api-reference-images), [video](https://videorouter.sh/docs/api-reference-video), [lip-sync](https://videorouter.sh/docs/api-reference-lipsync), [общий API](https://videorouter.sh/docs/api-reference), каталог конкретных моделей. Ссылки — точки для будущей проверки, не утверждение, что их содержимое перепроверено при сохранении handoff.

Зафиксировать точные response schemas, способ ожидания, представление нескольких outputs, схемы референсов, TTL, размеры и fallback-поведение. Скриншоты и названия capabilities не заменяют эту сверку.
