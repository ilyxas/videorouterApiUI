# Workflow v2: Steps, DAG, typed cards, execution session

Поставка 17 ноября 2026 по прямому поручению Ильи: реализовать архитектуру и проверить два Steps — `Text → Image → Edit Image`, затем `Video from references` (output редактирования + локальный файл). Этот документ заменяет указание «сначала replan» из исторического документа 09. Начинать чтение с [README](README.md).

## Архитектура

```text
Workflow v2
  Step 1 [continueOnSuccess=true]
    ImageCard (text-to-image) ── images[0] ──> ImageCard (image-edit)
  Step 2
    ImageCard output из Step 1 ── input_references[0] ──> VideoCard
    local asset               ── input_references[1] ──> VideoCard
```

- Workflow — упорядоченные Steps. Step содержит `nodes`, `edges`, `continueOnSuccess`, `enabled` (оба по умолчанию true) и `view` (`cards`/`flow`). Continue=false останавливает runner после выполненного активного Step. Отключённые Steps не останавливают run.
- Node — определение API-карточки: стабильный `id`, `kind`, `operationId`, `op`, `model`, `parameters`, `inputs`, `quoteFacts` и editor state. `ImageCard`, `VideoCard`, `AudioCard` наследуют `BaseCard`. Тип определяется выходом, поэтому lip-sync/face-swap/avatar — Video, transcription — Text. `ApiCard` сохраняет произвольные операции.
- Edge содержит `from {stepId,nodeId,port,outputIndex}` и `to {nodeId,port,slot}`. Ссылка разрешена на тот же или любой предыдущий Step. Компилятор отклоняет циклы, будущие зависимости, неверные типы и неоднозначные входы. Готовые узлы выполняются последовательно в стабильном топологическом порядке; параллельной генерации и неявного fan-out нет.
- Registry/Strategy описывает режимы, входы, поля и проверки. Factory создаёт тип карточки. Input/output adapters преобразуют API-медиа в типизированные артефакты. Compiler строит план; Runner хранит состояния и checkpoints. SQLite остаётся repository через существующий слой сервера.

## Local Grok CLI execution

Studio now supports `grok-cli/image` and `grok-cli/video` as additional execution models inside the existing ImageCards and VideoCards. The workflow schema remains version 2. `public/grok-profile.mjs` defines their shared capabilities and validation; `grok-cli.mjs` runs the local agent; `server.mjs` routes these model IDs locally. Existing VideoRouter requests, credentials, estimates, webhook delivery, and polling keep their existing transport. Grok-only workflows require no VideoRouter keys and record $0 additional cost under Ilya's existing Grok access.

Image generation/editing and text/image/reference-to-video are implemented. Video supports integer durations of 1–15 seconds, 480p/720p, and up to 14 image references. Image-to-video also accepts an optional last frame. CharacterCards, LocationCards, previous image outputs, local uploads, and HTTPS references use the normal typed input system. Grok's zero-based `<IMAGE_N>` labels are renumbered when missing sources are omitted; explicitly naming an absent reference skips the dependent card. Disabled Steps with saved outputs continue supplying those outputs without generation.

Grok is an agent, not a direct video API. A video card may make up to three intermediate image operations before one final video; an image card requests one generation or edit. These are instructions monitored through tool events, not an atomic pre-execution tool budget. Each card exposes only its final artifact at output index 0. Intermediate media and actual tool arguments are retained in the run result. Settings report executable and credential-file availability; the workflow editor shows supported fields, local zero cost, and current tool progress.

Each attempt uses a fresh UUID session and an isolated working directory under `data/grok-attempts`. Only media tools and `read_file` are enabled; shell commands, subagents, web search, memory, managed MCP tools, and automatic updates are disabled. The process uses the existing local Grok login without inheriting VideoRouter or XAI API keys. This tool allowlist is not an OS filesystem sandbox. References are staged locally, output paths are restricted to that attempt's Grok session, and verified media files are imported into `data/files`. No arbitrary executable, filesystem path, or session ID is accepted from workflow JSON.

Grok calls are serialized. A 15-minute timeout stops the process; failed/interrupted attempts are not automatically regenerated. Recover checks persisted results and the original session log, and can import a completed result without submitting another job. Account availability, login expiry, model behavior, and remaining usage are controlled by Grok. The initial adapter excludes audio/video references and explicit image pixel resolution. Requested video resolution does not guarantee exact file dimensions.

The agent contract links [grok-cli.json](../contracts/workflow/grok-cli.json) with exact local models and fields. Existing skills' explicit model allowlists have not been changed; an agent must be authorized to choose Grok. Import on another machine warns that Grok CLI and a working login are required there.

## DataCards and global Workflow Flow

`DataCard` is an abstract, non-executing data base. `CharacterCard` was implemented on 19 November 2026; `LocationCard` was added on 20 November. It is separate from the API `BaseCard` hierarchy. Workflow v2 now supports optional root `dataCards` and `view: steps|flow`; older workflows remain valid without them.

Character profiles contain name, description, age, appearance, scenario notes, and typed/described local assets. Location profiles contain name, description, appearance, spatial `layout`, scenario notes, and assets; they have no age field. A location can describe an arbitrary place, with rooms/exteriors/viewpoints as individually described assets. Both kinds support image references and base videos; audio uses `voice` for characters and `ambience` for locations. Assets use stable logical IDs and separate registered file IDs. Both library kinds use the existing SQLite `records` table with kind `data-card`; bytes remain in `data/files`. Adding a library card creates an independent workflow snapshot. Duplicate/scenario copies get new card IDs. A workflow cannot contain the same card ID twice. Deleting a library entry preserves snapshots and files.

API input bindings `{dataCardId, assetId}` resolve through the workflow snapshot. The shared resolver supports input selection, estimate invalidation, preflight, and runtime materialization. The runner never executes or bills a DataCard. Removing a referenced snapshot/asset explicitly clears the affected slots to missing inputs without reordering other references. Running snapshots remain fixed; paused workflows can revise them for subsequent execution. Existing completed outputs and their original configurations are retained.

JSON includes character metadata and registered file IDs, but no media bytes or filesystem paths. Known files reconnect by ID and compatible media type; absent files retain metadata and require reattachment. Ordinary local inputs retain their previous portable-import behavior. Unused missing character assets do not block execution. The server checks referenced files before executing active Steps.

The Characters and Locations library pages support create/edit/duplicate/delete. Agent-context export on either page includes both kinds. The workflow source panel and typed input picker distinguish the kinds while supporting ordered combinations. A saved card cannot change kind under an existing ID. New local endpoints: `GET /local/data-cards`, `GET /local/data-cards/context`, `POST /local/data-card`, and `POST /local/data-card/:id/duplicate`. Existing deletion preview/ticket endpoints accept `kind: data-card`. Host/Origin/X-Studio protections remain in force.

Workflow Flow renders each CharacterCard and LocationCard once, Step groups, generated-output edges, character/location asset bindings, and raw response dependencies. Character connections are purple and location connections are teal. Desktop groups run left to right. On screens up to 760 px, a vertical layered DAG replaces the initial wrapped-row attempt: dependencies run downward, parallel cards share a layer, and a parent-based ordering pass reduces crossings. Step labels occupy a separate left column. Connections use top/bottom ports and rounded orthogonal paths; links skipping layers receive separate side lanes, reused only for non-overlapping vertical intervals. The mobile graph remains at 70% scale and grows to its full height. Wide parallel branches retain their topology and can scroll horizontally rather than folding into new rows.

Selecting an API card highlights its connections, dims unrelated lines, shows the connection labels below the graph, and opens the existing editor/output. CharacterCards and LocationCards open their respective snapshot editors. Resizing recalculates only graph geometry without rebuilding an open editor. Step controls remain below the overview. This is the existing SVG/HTML graph with a deterministic local layout algorithm; it does not add drag-to-connect editing or a third-party graph dependency. Very complex graphs can still have edge crossings; the verified guarantee is that routed segments avoid cards and Step labels. The 20 November 2026 presentation update is served through existing static routes and requires a browser refresh, not a backend restart.

The contract is now documentation/tooling version 3 while its output remains workflow version 2. Its schema distinguishes CharacterCards and LocationCards, their fields and asset roles, and their shared bindings; the offline validator accepts `--asset-context FILE` and separates structural validity from local-asset readiness. ## Управление Steps и сессия выполнения

18 ноября добавлены удаление непустого Step вместе со связями после подтверждения, ↑/↓ с проверкой порядка зависимостей и локальный для Step переключатель Flow/Карточки. Layout раскладывает DAG слева направо по топологическим колонкам; параллельные ветки располагаются вертикально. Квадраты показывают тип, режим, модель, статус и миниатюру; внешние входы подписаны. Нажатие квадрата открывает полную карточку под графом. Фоны карточек чередуются белый / `#f7f5fa`.

`enabled=false` исключает все вызовы Step: pricing, uploads и generation. По паре workflow ID + node ID берётся последний успешный output либо явно закреплённый run. Reused строки не создают новые кандидаты. Снимок источников фиксируется при prepare, включая пока включённые Steps, чтобы их можно было выключить до начала выполнения. Проверяется известный TTL и наличие локального файла. Reused row хранит `reusedFrom`, artifacts и cost=0; старый source cost виден отдельно. Удаление Step не удаляет runs/assets. Старые схемы без новых полей продолжают работать.

Недоступный источник убирается из inputs до pricing/materialization. Если обязательных входов недостаточно, зависимый Node получает skipped с причиной; пропуск распространяется по зависимостям, независимые узлы продолжаются. Для исчезнувшего reference пересчитываются номера `@ImageN` / `@VideoN` / `@AudioN`; если prompt явно требует удалённый reference, карточка пропускается. Сломанная конфигурация без отсутствующего источника остаётся обычной ошибкой валидации.

UI запускает и показывает run на странице workflow, включая медиа между Steps. Лёгкий polling не передаёт raw result/request и обновляет изменившиеся outputs, сохраняя проигрывание медиа. Во время running доступны enabled только будущих Steps и Continue/Pause. **На паузе редактируются все Steps**, включая уже выполненные; это исправление по уточнению Ильи от 18 ноября. Ревизия проверяется на сервере и отклоняет гонку с началом Step. Второй running run того же workflow запрещён.

Кнопка **«Запустить Step»** в заголовке каждого Step выполняет только его DAG, даже если Step выключен для общего запуска. Предыдущие Steps поставляют выбранные сохранённые outputs без генерации, последующие не включаются в этот запрос. Используются существующие prepare/run с `stepId`; при паузе передаются `parentRunId` и `parentRevision`. Отдельный run хранит `scopeStepId` и `parentRunId`; исходный run остаётся paused. UI возвращается к нему после завершения отдельного Step, показывает отдельный расход и сохраняет черновик. Неудачная перегенерация не удаляет прежний успешный output. Новый успешный output выбирается как latest, старые можно закрепить вручную; выбор сразу меняет preview.

Resume принимает текущую схему без восстановления старых параметров поверх правок. Пройденные Steps определяются по стабильным ID, их выбранные outputs берутся из истории (в том числе из отдельного запуска Step); сами Steps автоматически не перегенерируются. Изменённые параметры начинают влиять на output только после явного запуска Step. При смене выбранного output прежние запросы/результаты архивируются в `revisions[].steps`, расходы переносятся в `carriedCost`, а прежние outputs остаются кандидатами для pin. Неизменённые outputs сохраняются со своими исходными параметрами в `outputDefinition`. Расход child run учитывается в его собственной истории; parent не теряет прежние списания и не начисляет child cost повторно. История показывает архив предыдущих запросов. Новые Steps выполняются при продолжении; уже пройденные, даже переставленные, поставляют выбранный output. Если отдельно выполнить ещё не пройденный Step, общий workflow при продолжении по-прежнему учитывает его «Включён»: для использования результата без повторного вызова выключите его.

Новые маршруты: `GET /local/workflow/:id/outputs` (кандидаты и active/last run), `GET /local/run/:id?view=workflow` (компактный статус), `POST /local/run/:id/control` (`revision`, `stepId`, `enabled`, `continueOnSuccess` или `pauseAfterCurrent`). Существующие prepare/run/resume используются с reuse snapshot. История, API Explorer и оценка остаются общими; budget исключает отключённые и заведомо skipped карточки.

## References, стоимость и сохранность

URL используется напрямую. Небольшой локальный файл или base64 output передаётся как data URI внутри `input_references` либо другого media input. Upload fallback нужен только URL-only операции или когда inline body превысил бы 8 MiB. Локальный выбор файла не отправляет его внешнему провайдеру. Перед запросом проверяются наличие и тип источника, output index и известный TTL.

Preview цены работает отдельно от запуска, пропускает ещё не полученные references и сообщает об этом. Перед каждым Image/Video вызовом повторная оценка использует фактические разрешённые параметры; несовпадающие явные assumptions останавливают вызов. Неизвестная токенная стоимость остаётся неизвестной до результата. Оценка не является лимитом биллинга. История хранит quote, фактический request, remote ID, artifacts и известный cost.

Существующие v1 workflow, runs и assets не удалены. При сохранении открытого v1 создаётся отдельная v2-копия. Позиционные ссылки переводятся в стабильные ссылки на Node. Draft, API editor round-trip и история поддерживают v2. На паузе можно редактировать все Steps; результаты и расходы прежних запросов сохраняются, ревизии архивируются.

Runner не повторяет неизвестный POST автоматически. Поддерживаемые create endpoints получают стабильный Idempotency-Key. Recover обращается только к существующему remote job через GET. Продолжение возможно на полностью завершённой границе Step; частично выполненный Step требует нового явного workflow для оставшихся операций. Ключи и чувствительные API-ответы остаются в памяти, не в Git.

## Контракт построения workflow внешним агентом

Контракт принимает обычную пользовательскую задачу и контекст приложения; готовый граф от пользователя не требуется. Агент выбирает операции, IDs, группировку и зависимости, возвращая JSON без исполнения. Готовые творческие решения могут поступать из задачи или скиллов раскадровки/модельных промптов. Рабочая точка входа — [contracts/workflow/README.md](../contracts/workflow/README.md), рядом `workflow.schema.json`, `operations.json`, `registry.mjs` и `validate.mjs`. Mocks в контракт не включены.

Contract v2 emits canonical workflow **version 2**, including optional workflow-level CharacterCards and their asset bindings. Он фиксирует Step/Node/Edge, точные operation tuples и порты, порядок и нулевую индексацию references, размещение рёбер в принимающем Step, смешанные типы карточек и внутри-/межэтапные зависимости. API parameters остаются открытым объектом; suggested fields реестра не становятся списком обязательных полей. Возможности моделей поступают из задачи/профиля, не выводятся из наличия generic operation. По умолчанию Steps включены и продолжаются автоматически; pause — только при явном решении задачи. Авторский профиль строже импортера: неизвестные структурные поля отклоняются вместо молчаливой потери.

Portable import creates a new workflow ID without history/pins. Ordinary local files require reattachment; CharacterCard file IDs reconnect only when present with the correct media type. Disabled Steps do not acquire another workflow’s outputs. The schema represents missing inputs explicitly; agents must not invent URLs, assets, or extra generations to hide unresolved requirements.

CLI `node contracts/workflow/validate.mjs FILE [--ready]` проверяет ограниченный набор JSON Schema keywords, использованных в приложенном schema, плюс семантику через настоящий `parseWorkflowJSON`/compiler и локальный execution preflight. Это не универсальная реализация JSON Schema. Без `--ready` допускается импортируемый незаполненный draft; с ним известные отсутствующие execution inputs дают exit 1. Оба режима не используют сеть, БД, uploads, pricing или generation. Реестр берётся из `public/operations.mjs`; `registry.mjs --check` проверяет соответствие, `--write` обновляет snapshot offline.

Точные запросы агентам, отдельные mocks и результаты прогонов находятся в [документе тестов](../tests/TESTING.md#что-именно-отправлялось-агентам). Skills и встроенная интеграция помощника не реализованы.

## Webhook + polling: первая стадия

18 ноября по прямому поручению Ильи внедрён webhook параллельно с polling. Прежний интервал сохранён: 4 секунды в graph runner и для legacy Video/Jobs, 15 секунд для legacy Batch. Платные запросы и реальная доставка VideoRouter в этой поставке не выполнялись.

- `webhooks.mjs` содержит отдельный HTTP-приёмник, привязку попыток и SQLite-таблицы `webhook_attempts` / `webhook_inbox`. HMAC-SHA256 проверяется по raw body отдельным секретом организации; проверяются событие и job ID, body ограничен 2 MiB. Доставка сохраняется до 204 и дедуплицируется. Приёмник предоставляет только GET `/health` и POST `/webhooks/videorouter/<attemptId>`; UI, assets и local API через него недоступны.
- До POST создаётся уникальная попытка с run/node/path и callback URL. Поддержаны документированные `/v1/videos`, `/v1/lipsync`, `/v1/face-swap`, `/v1/jobs`, в v2 и прежнем API runner. Остальные endpoints сохраняют поведение. Явные null/сторонний `webhook_url` не заменяются. Callback добавляется после оценки, не меняя содержимое генерации или quote assumptions.
- Первый терминальный ответ становится сохранённым результатом попытки. Webhook только будит существующий runner; следующие карточки и Steps выполняет исключительно runner. Незавершённый GET после webhook не заменяет output, но может дополнить отсутствующую цену. Доставка до ответа POST сохраняется и связывается после получения remoteId.
- Стоимость присваивается конкретной попытке, не суммируется за каждую доставку. Поздняя цена учитывается также у архивированной попытки через carriedCost, не меняя выбранный output и не начисляя расход reused строке. Если терминальный ответ не содержит цены, GET повторяется каждые 4 секунды до часа; после перезапуска незавершённая сверка снова подхватывается. Уже известная терминальная цена не заменяется запоздалым ответом.
- Pause, Run Step, выключенные Steps и pinned outputs не изменены. После перезапуска сохранённые события доступны через прежний Recover; полученное до ответа POST уведомление позволяет восстановить job ID. Новые POST автоматически не создаются. Recover остаётся явным действием пользователя и соблюдает прежнее ограничение восстановления на завершённой границе Step.

В «Подключение» добавлены публичный URL и password-поле webhook secret. URL/включение сохраняются в SQLite; секрет — только в памяти, не возвращается local API и не записывается в историю. Приёмник включается после подключения секрета на `127.0.0.1:8792` (по умолчанию PORT+1, настройка WEBHOOK_PORT). После перезапуска секрет вводится снова либо передаётся через окружение. Полная инструкция и отключение — в [README проекта](../README.md#webhook--polling).

Webhook может запаздывать ради финальной цены; polling поэтому сохраняется. Спящий Mac не получает запросы: Funnel не является постоянным inbox вместо приложения.

## Ограничения

Webhook-приёмник не публикует UI, assets или local API. Rate limiting отсутствует; приёмник использует общий Node-процесс со Studio. Публичный Funnel допускает обращения интернет-клиентов; принятие события защищено HMAC. Границы выполненной проверки описаны в [документе тестов](../tests/TESTING.md).

Реестр охватывает описанные API media-операции, но все сочетания моделей/хостов не проверены реальными вызовами. Общие поля можно уточнять через API Explorer. Доступность модели определяет провайдер. Realtime/live остаются отдельными существующими инструментами. Маски inpainting не добавлялись. Полноценный свободный canvas с перетаскиванием рёбер не требуется для схемы DAG: UI задаёт связи через типизированные входы.
